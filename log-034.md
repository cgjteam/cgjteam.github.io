# Log 034 - Architectural Principles Emerging from the Geometry Library

**Date:** 2026-07-28

## Objective

The previous stages of the project produced several local architectural decisions:

- separation of the Hilbert, Tarski and Suppes formalizations;
- removal of the temporary shared `GeometryCore`;
- reduction of unnecessary Mathlib dependencies;
- introduction of the local `UnorderedPair` abstraction;
- simplification of the Suppes module structure.

The purpose of this log is not to describe another isolated refactoring.

Instead, it records the general architectural principles that emerged from these experiments and now guide the further development of the geometry library.

---

## 1. Each Foundational Formalization Owns Its Primitive Structure

The Hilbert, Tarski and Suppes paths are not merely different collections of axioms over a common primitive model.

Each path has its own logical organization, primitive predicates and intended development direction.

The project therefore maintains three independent foundational frameworks:

```text
Hilbert
Tarski
Suppes
```

Each framework owns its own primitive geometric structure.

This decision prevents artificial coupling between formalizations whose apparent syntactic similarity does not reflect genuine mathematical identity.

A common primitive `GeometryCore` should not be introduced merely because several frameworks contain a type of points or a relation interpreted geometrically.

Shared foundations must arise from a real common abstraction, not from superficial similarity.

---

## 2. Foundational Independence Does Not Exclude Technical Reuse

The rejection of a common geometric core does not imply that all implementation infrastructure must be duplicated.

The local type

```lean
UnorderedPair
```

is an example of legitimate reuse.

Both the Hilbert and Tarski paths require an unoriented pair of endpoints for the representation of segments.

This construction is:

- mathematically elementary;
- independent of any particular axiom system;
- technically identical in both formalizations;
- too small to justify a broad external dependency.

It is therefore appropriate as a shared local implementation component.

The resulting distinction is important:

```text
shared geometric foundation     - rejected
shared technical abstraction    - accepted
```

The project should share only those components whose meaning is genuinely independent of the foundational theory.

---

## 3. A Source File Should Represent a Mathematical or Architectural Module

During the development of the Suppes path, some intermediate proof steps were extracted into separate files.

This was useful while the argument was being constructed, but it did not always produce a meaningful final architecture.

For example,

```text
ParallelogramRecognitionSuppes.lean
```

contained one temporary axiom and one theorem used directly in the proof of the midsegment theorem.

It did not define an independent theory of parallelogram recognition and did not provide a substantial reusable public interface.

Its contents were therefore moved into

```text
MidsegmentParallelSuppes.lean
```

The general principle is:

> A separate file should correspond to a stable mathematical theory, a foundational layer, a reusable interface, or a major proof.

A file should not remain separate merely because a short stage of one proof was temporarily developed in isolation.

Development modules and final library modules need not have the same boundaries.

---

## 4. Stable Interfaces Should Be Separated from Foundational Implementations

The project increasingly distinguishes between:

- primitive structures and axioms;
- geometric interfaces;
- concrete theorem proofs.

Typical interface concepts include:

```text
IsMidpoint
IsMedian
IsParallelogram
Parallel
Congruent
```

These names express mathematical concepts rather than details of Lean implementation.

The interface layer provides a vocabulary in which later proofs can be written.

This makes it possible to preserve the mathematical structure of a proof even when its foundational implementation changes.

The intended dependency direction is:

```text
primitive structure
        |
        v
axioms
        |
        v
geometric interface
        |
        v
theorem proofs
```

The reverse dependency should be avoided.

A foundational module should not contain declarations introduced only because one later proof happens to need them.

---

## 5. Proof Files Are Clients of the Theory

The files

```text
MidsegmentParallel.lean
FinlayProof.lean
```

and their Suppes counterparts are not parts of the primitive theory.

They are applications of that theory.

This distinction is important because it determines where missing facts should be placed.

If a proof requires a reusable geometric fact, that fact should be introduced in an interface or theory module.

If it represents a temporary or explicitly assumed principle of a particular foundational path, it should be named and located accordingly.

The final proof file should remain a readable reconstruction of the mathematical argument rather than becoming a repository of ad hoc infrastructure.

This principle was especially important during the formalization of Finlay's proof.

---

## 6. Similar Module Shapes Are Useful, but Exact Uniformity Is Not Required

After the recent simplifications, the main Hilbert and Suppes paths have comparable structures.

Hilbert:

```text
HilbertCore.lean
HilbertAxioms.lean
HilbertInterface.lean
MidsegmentParallel.lean
FinlayProof.lean
```

Suppes:

```text
SuppesCore.lean
SuppesAxioms.lean
SuppesInterface.lean
MidsegmentParallelSuppes.lean
FinlayProofSuppes.lean
```

This parallel organization makes the two developments easier to compare.

However, similarity of module shape is not itself a requirement.

The Tarski path may require a different internal decomposition because its primitive language and proof mechanisms are different.

Architectural symmetry is useful only where it reflects mathematical symmetry.

It should not be imposed mechanically.

---

## 7. External Dependencies Should Be Proportional to Their Use

The replacement of Mathlib's `Sym2` by the local `UnorderedPair` abstraction revealed a broader principle.

An external dependency is justified when it provides substantial mathematical or technical infrastructure used by the project.

It is less justified when a large transitive dependency graph is imported for a very small construction that can be stated locally and transparently.

The goal is not to eliminate Mathlib as a matter of principle.

The goal is to ensure that every dependency has a clear role.

The project should therefore prefer:

- narrow imports over broad imports;
- local elementary definitions over disproportionately large dependencies;
- explicit dependency boundaries;
- periodic inspection of the transitive build graph.

The significant reduction in the number of `lake build` tasks demonstrated that import decisions have measurable architectural consequences.

---

## 8. The Library Is Developing Its Own Mathematical Language

The project is no longer only a collection of Lean encodings of isolated proofs.

A stable mathematical vocabulary is gradually emerging.

This vocabulary includes:

- primitive geometric relations specific to each foundational theory;
- common high-level notions such as midpoint, median and parallelogram;
- theorem-level structures corresponding to classical proof steps;
- local implementation abstractions such as `UnorderedPair`.

This emerging language is one of the most important results of the project.

It provides a layer between informal synthetic geometry and the details of a particular axiomatic backend.

The long-term objective is not necessarily to force every formalization through one identical interface.

Rather, it is to identify which parts of classical geometric reasoning admit stable formal expression across different foundational systems.

---

## 9. Hilbert, Tarski and Suppes Are Comparative Formalization Paths

The three frameworks should not be understood as competing implementations from which one must eventually be selected.

They form a comparative environment for studying formal geometric reasoning.

The same geometric theorem may require:

- different primitive assumptions;
- different intermediate constructions;
- different proof lengths;
- different forms of degeneracy control;
- different interfaces between human reasoning and the formal system.

This comparative structure is itself a research object.

It can reveal which parts of a classical proof are:

- genuinely geometric;
- consequences of a particular axiom system;
- hidden uses of stronger structure;
- implementation artifacts introduced by the prover.

The separation of the three paths therefore supports both software modularity and mathematical analysis.

---

## 10. Refactoring Is Part of the Mathematical Investigation

The architectural experiments were not merely software maintenance.

The unsuccessful attempt to create a common `GeometryCore` showed that the Hilbert and Tarski primitive structures should remain independent.

The removal of `ParallelogramRecognitionSuppes` showed that the recognition theorem belonged to the local proof architecture rather than to an independent theory.

The migration from `Sym2` to `UnorderedPair` identified a real shared abstraction at the implementation level.

Each refactoring therefore answered a structural question about the formal mathematics.

In this project, code organization is not external to the research.

It is one of the tools used to determine:

- where mathematical concepts begin and end;
- which assumptions belong to a theory;
- which constructions are reusable;
- which similarities between formalizations are genuine.

---

## Current Architectural Principles

The following principles summarize the present state of the project:

1. Each foundational system owns its primitive geometric structure.
2. Common foundations are introduced only when a genuine common abstraction exists.
3. Small theory-independent technical abstractions may be shared.
4. A source file should represent a meaningful mathematical or architectural unit.
5. Stable geometric interfaces should be separated from primitive axioms.
6. Proof files should remain clients of the theory.
7. Similar formalization paths may have comparable organization without forced uniformity.
8. External dependencies should be narrow, explicit and proportional to their use.
9. Refactoring decisions should be evaluated mathematically as well as technically.
10. The comparative study of different formalization paths is a central objective of the library.

---

## Conclusion

The architecture of the geometry library was not designed completely in advance.

It emerged through repeated formalization, failed abstractions, local experiments and successful reductions.

The current structure reflects a balance between two requirements:

- preserving the independence of distinct foundational theories;
- sharing only those concepts and tools that are genuinely common.

This balance provides a stable basis for the next stage of development.

The project can now continue not only by proving further geometric theorems, but also by studying the formal languages through which those theorems become expressible in Hilbert, Tarski and Suppes geometry.

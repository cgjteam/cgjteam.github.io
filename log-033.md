# Log 033 - Reducing Dependencies and Simplifying the Project Architecture

**Date:** 2026-07-28

## Objective

The purpose of this work was to simplify the implementation architecture of the geometry library after the separation of the Hilbert, Tarski and Suppes formalization paths.

The main goals were:

- to remove unnecessary dependencies on Mathlib;
- to replace external technical infrastructure with a local abstraction where appropriate;
- to eliminate auxiliary modules that did not represent independent mathematical layers;
- to reduce the size and complexity of the project dependency graph.

This stage did not introduce new geometric results. Its purpose was architectural consolidation.

---

## Local Representation of Unordered Pairs

The Hilbert formalization represented unoriented segments and angles using Mathlib's

```lean
Sym2
```

type.

Although mathematically appropriate, this introduced a dependency on

```lean
Mathlib.Data.Sym.Sym2
```

for a very small and elementary construction.

A new local module was therefore introduced:

```text
UnorderedPair.lean
```

It defines:

- the equivalence relation identifying `(a, b)` with `(b, a)`;
- the corresponding quotient type `UnorderedPair`;
- the constructor `UnorderedPair.mk`;
- the fundamental symmetry theorem `UnorderedPair.eq_swap`.

The implementation provides exactly the functionality required by the geometry library without importing the full Mathlib `Sym2` infrastructure.

---

## Migration of the Hilbert Formalization

The Hilbert core was migrated from

```lean
Sym2 Point
```

to

```lean
UnorderedPair Point
```

for segment congruence.

The representation of unoriented angles was also migrated from

```lean
Point x Sym2 (Set Point)
```

to

```lean
Point x UnorderedPair (Set Point)
```

The following parts of the Hilbert interface were adapted:

- segment construction;
- segment endpoint reversal;
- congruence reversal in the first segment;
- congruence reversal in the second segment;
- angle construction;
- angle endpoint reversal.

The public four-point congruence interface and the downstream geometric proofs were preserved.

After the migration, the import

```lean
Mathlib.Data.Sym.Sym2
```

was removed from the Hilbert path.

The remaining set-theoretic operations required by the Hilbert axioms were supplied through the more appropriate import

```lean
Mathlib.Data.Set.Lattice
```

---

## Migration of the Tarski Formalization

A later inspection showed that the Tarski core still depended directly on

```lean
Mathlib.Data.Sym.Sym2
```

for its representation of unoriented segments.

The local `UnorderedPair` abstraction was therefore recognized as a genuinely shared implementation component rather than an internal detail of the Hilbert formalization.

The Tarski definitions

```lean
SegmentCongruent
```

and

```lean
Segment
```

were migrated to `UnorderedPair`.

The segment symmetry theorem and both congruence reversal theorems were adapted accordingly.

This removed the final direct use of `Sym2` from the project.

As a result, both foundational paths now use the same local representation:

```text
HilbertCore -> UnorderedPair
TarskiCore  -> UnorderedPair
```

while retaining separate primitive geometric structures and namespaces.

---

## Simplification of the Suppes Path

The Suppes formalization had accumulated several auxiliary and experimental modules during development.

Two modules were removed from the active architecture:

```text
SuppesIntersection.lean
SuppesCentroidProof.lean
```

These files no longer belonged to the main proof path.

A further inspection concerned

```text
ParallelogramRecognitionSuppes.lean
```

This module contained only:

- the temporary axiom `parallel_vertex_unique`;
- the theorem `parallelogram_of_opposite_sides_parallel`.

Both declarations were used directly as part of the Suppes proof of the midsegment theorem.

They did not constitute an independent mathematical theory or a reusable public module.

The contents of `ParallelogramRecognitionSuppes.lean` were therefore moved into

```text
MidsegmentParallelSuppes.lean
```

and the separate module was deleted.

Imports in

```text
FinlayProofSuppes.lean
CGJteamLab.lean
```

were updated to reflect the new structure.

---

## Resulting Suppes Architecture

After the reduction, the main Suppes path consists of five modules:

```text
SuppesCore.lean
SuppesAxioms.lean
SuppesInterface.lean
MidsegmentParallelSuppes.lean
FinlayProofSuppes.lean
```

This now mirrors the structural scale of the Hilbert path:

```text
HilbertCore.lean
HilbertAxioms.lean
HilbertInterface.lean
MidsegmentParallel.lean
FinlayProof.lean
```

The two formalizations remain mathematically independent, but their project organization is now easier to compare.

---

## Dependency Graph Reduction

The architectural changes produced a visible reduction in the number of build tasks reported by

```text
lake build
```

The task count decreased by approximately five hundred during the dependency cleanup.

This indicates that removing the broader Mathlib imports eliminated substantial transitive parts of the compilation graph.

The practical effect is not limited to source-code organization.

The project now has:

- fewer imported modules;
- a smaller transitive dependency graph;
- a clearer distinction between local geometric infrastructure and external library support;
- reduced rebuild scope after foundational changes.

---

## Technical Outcome

The completed refactoring included:

- introduction of the local `UnorderedPair` abstraction;
- removal of all direct uses of Mathlib `Sym2`;
- migration of Hilbert segments and angles;
- migration of Tarski segments;
- removal of obsolete Suppes experimental modules;
- integration of Suppes parallelogram recognition into the midsegment proof module;
- correction of all affected imports;
- successful compilation of the entire project.

The final verification was performed using

```text
lake build
```

and completed without errors.

---

## Architectural Conclusions

This work clarified two different forms of reuse.

The primitive geometric structures of Hilbert, Tarski and Suppes should remain independent because they represent distinct foundational systems.

Small implementation abstractions, however, may be shared when they express genuinely common technical structure.

`UnorderedPair` is such an abstraction.

It does not impose a common geometric foundation, but it provides a minimal local representation required independently by the Hilbert and Tarski paths.

The Suppes cleanup established a second principle: a separate source file should correspond to a meaningful mathematical or architectural module, not merely to a short intermediate step in one proof.

The resulting project is therefore both more independent from Mathlib and more disciplined in its internal modular structure.

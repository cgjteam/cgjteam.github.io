# Log 051 --- The Hilbert Plane Compatibility Bridge

## Preserving the existing plane theory above a source-faithful foundation

Log 050 introduced a new source-faithful Hilbert axiom layer in

``` text
CGJteamLab/HilbertAxioms.lean
```

That change created an immediate architectural problem.

The existing geometry library had already accumulated a large and useful
plane theory. Its public classes and theorem statements were written against
an older interface in which planar structure, derived notions, and some
representation choices were already packaged for convenient use.

The correct response was not to rewrite that theory.

Instead, the project introduced

``` text
CGJteamLab/HilbertPlaneAPI.lean
```

as a compatibility layer between the new source-oriented foundation and the
legacy plane vocabulary.

The intended architecture is

``` text
HilbertAxioms.lean
        |
        v
HilbertPlaneAPI.lean
        |
        v
HilbertPlaneTheory.lean
        |
        v
existing synthetic geometry
```

The central design rule is:

> The compatibility layer transports structure. It does not reproduce the
> derived plane theory.

This log records why that distinction matters and what the bridge currently
does.

## 1. Two interfaces describe different mathematical roles

The new foundational layer and the old plane API should not be identified
declaration by declaration.

`HilbertAxioms.lean` is organized around Hilbert's source system:

``` text
Group I     incidence in space
Group II    order
Group III   congruence
Group IV    parallel uniqueness
Group V     continuity
```

Planes occur explicitly where Hilbert requires them.

The legacy plane API, by contrast, was designed as a practical interface for
the existing planar theorem corpus. It contains declarations such as

``` text
HilbertIncidence
HilbertPlaneIncidence
HilbertOrder
HilbertCongruence
HilbertEuclideanPlane
HilbertArchimedeanPlane
```

and definitions such as

``` text
PrimCollinear
HilbertSameRay
HilbertSameSide
HilbertSegmentMeetsLine
```

These names remain important because a large part of the project already
depends on them.

The bridge therefore has two simultaneous obligations:

``` text
preserve source fidelity below
            +
preserve the working API above
```

Those obligations belong to different files.

## 2. The frozen legacy declarations are retained

The compatibility file currently imports both

``` text
CGJteamLab.HilbertAxioms
CGJteamLab.HilbertAxiomsWork
```

The roles are different.

`HilbertAxioms.lean` is the source-faithful foundation.

`HilbertAxiomsWork.lean` retains the frozen declarations of the old plane API.
It is not treated as the new foundational axiom system. Its purpose is to keep
the public vocabulary and type signatures required by
`HilbertPlaneTheory.lean`.

This is an important migration technique.

Instead of changing thousands of lines of derived theory merely because the
foundational representation has changed, the old API declarations are held
fixed while the relationship to the new foundation is made explicit.

Schematically:

``` text
new source layer              frozen legacy vocabulary
       |                               |
       +---------------+---------------+
                       |
                       v
               HilbertPlaneAPI
```

The frozen declarations are therefore compatibility infrastructure, not a
second target foundation.

## 3. Point-line incidence is the first direct bridge

The simplest compatibility step identifies the legacy incidence relation with
the primitive incidence relation already present in `Geometry.Geo`.

The bridge defines

``` text
hilbertIncidenceOfGrundlagen
```

with

``` text
OnLine := Geo.OnLine
```

Under this canonical incidence structure, legacy

``` text
PrimCollinear
```

is definitionally the same geometric condition as

``` text
HilbertGrundlagenCollinear
```

namely the existence of one line containing the three points.

This gives the first direct transport:

``` text
Hilbert Group I
      |
      v
legacy HilbertPlaneIncidence
```

The construction uses the source axioms I.1-I.3 and does not add a new
geometric assumption.

The bridge deliberately avoids installing a global ambient typeclass instance
at this stage.

## 4. The first three order axioms transport directly

Hilbert II.1-II.3 are also close enough to the old interface to admit direct
compatibility theorems.

The bridge supplies source-to-legacy forms of:

``` text
II.1   betweenness gives distinct collinear points and endpoint symmetry
II.2   segment extension
II.3   uniqueness of the middle point
```

These are local transport statements.

The difficulty begins with Pasch.

## 5. Pasch exposes the spatial-versus-planar boundary

In the source-faithful system, Hilbert II.4 is explicitly planar.

The data include:

``` text
triangle ABC
plane pi containing A, B, C
line l contained in pi
```

together with the usual nonincidence and segment-intersection hypotheses.

The legacy `HilbertOrder.pasch` field suppresses the plane parameter because
the old API was designed for plane geometry.

In three-dimensional ambient geometry these statements cannot simply be
identified.

A line in space may be disjoint from parts of a triangle for spatial reasons
that have nothing to do with planar separation. Therefore a global ambient

``` text
HilbertOrder Geo
```

would be the wrong compatibility object.

This observation determines the central construction of the bridge.

## 6. A fixed Hilbert plane becomes its own geometry

For every source-faithful Hilbert plane `pi`, the bridge constructs an induced
geometry.

Its point type is

``` text
HilbertPlanePoint Geo pi
```

consisting of ambient points lying in `pi`.

Its line type is

``` text
HilbertPlaneLine Geo pi
```

consisting of ambient lines wholly contained in `pi`.

Incidence, betweenness, segment congruence, rays, and angle data are inherited
from the ambient geometry.

The resulting geometry is

``` text
HilbertPlaneGeo Geo pi
```

This construction changes the problem from

``` text
make planar axioms true globally in space
```

to

``` text
restrict the source geometry to one actual plane
and recover the legacy planar interface there
```

This is the mathematically correct direction.

## 7. The induced plane recovers the legacy incidence and order layers

Once the carrier has been restricted to a fixed plane, the bridge constructs
legacy instances for

``` text
HilbertIncidence (HilbertPlaneGeo Geo pi)
HilbertPlaneIncidence (HilbertPlaneGeo Geo pi)
HilbertOrder (HilbertPlaneGeo Geo pi)
```

The Pasch field can now be obtained from source II.4 because all points and
lines in the induced geometry already carry proofs that they lie in `pi`.

Thus the plane parameter has not disappeared by assumption.

It has been absorbed into the type of the induced geometry.

This is an important general pattern:

``` text
explicit spatial parameter
        |
        v
subtype / induced structure
        |
        v
planar API without an explicit parameter
```

## 8. Segment congruence transports without rebuilding theory

The first three axioms of Group III are transported on the induced plane.

The bridge contains compatibility results corresponding to

``` text
III.1   segment construction
III.2   common-segment congruence
III.3   segment additivity
```

The essential mechanism is straightforward.

A source construction may first produce an ambient point. Group I is then used
to prove that the constructed point remains in the chosen plane, after which
the point is repackaged as an element of `HilbertPlanePoint Geo pi`.

This is transport, not a new proof of plane geometry.

No attempt is made here to redevelop the later congruence calculus, triangle
theory, or Hilbert's derived theorems.

## 9. Same-side and ray notions require explicit transport

The old and new formulations do not use exactly the same internal
representations for every auxiliary notion.

The bridge therefore proves equivalences for the objects needed by angle
construction.

For same-side reasoning it relates

``` text
HilbertSameSide
```

in the induced plane to

``` text
HilbertGrundlagenSameSideInPlane
```

in the source-faithful ambient formulation.

For rays it proves that membership in a ray of the induced plane is exactly
membership in the corresponding ambient ray after forgetting the subtype
proofs.

The relevant pattern is

``` text
plane object
    |
forget subtype proof
    |
    v
ambient object
```

together with the reverse fact that a point generated by the relevant
in-plane construction remains in the plane.

These results are technical, but their architectural purpose is narrow:
they align representations across the boundary.

## 10. Angle congruence is the most delicate compatibility point

The largest mismatch concerns angle congruence.

The source-faithful foundation uses the primitive relation

``` text
Geo.UnorientedAngleCongruent
```

through

``` text
HilbertGrundlagenAngleCongruent
```

The legacy working language uses

``` text
Geo.AngleCongruent
```

which is constructed as an equivalence closure using `Relation.EqvGen`.

Therefore the two layers have different logical content.

The source layer is intentionally designed so that reflexivity, symmetry, and
transitivity are not silently inserted into primitive angle congruence.

The legacy relation is intentionally convenient for later theorem proving.

The bridge must respect both facts.

## 11. The induced primitive angle relation is restricted to actual angles

`HilbertPlaneGeo` does not allow arbitrary raw angle data to acquire geometric
meaning merely because it has the correct type.

The bridge records when raw angle data actually arise from three plane points.

Conceptually:

``` text
A, B, C in pi
      |
      v
point-generated angle data
      |
      v
actual induced-plane angle
```

Primitive congruence in the induced geometry is then ambient primitive angle
congruence restricted to such actual angle data.

This prevents the compatibility construction from assigning geometric
content to arbitrary representation artifacts.

## 12. The current angle bridge is intentionally one-way

For actual point-generated angles, the bridge proves:

``` text
source primitive angle congruence
              |
              v
induced-plane primitive angle congruence
              |
              v
legacy EqvGen AngleCongruent
```

The final step uses the generating constructor of `Relation.EqvGen`.

This direction is mathematically harmless: every primitive congruence is a
member of its equivalence closure.

The converse is not built into the bridge.

That is deliberate.

An arbitrary path in an equivalence closure contains derived reflexivity,
symmetry, and transitivity information. Recovering a source primitive
congruence statement from such a path would require theorem-level geometry,
not mere representation transport.

This observation was the key warning against allowing the adapter to grow
into a second copy of `HilbertPlaneTheory`.

## 13. The rejected direction: rebuilding Hilbert theory inside the adapter

During development it became tempting to prove more and more results inside
`HilbertPlaneAPI.lean` in order to reconstruct every field of the enriched
legacy congruence interface directly from the new source layer.

That route began to reproduce results belonging to the existing plane theory,
including order, ray, Pasch, and triangle-congruence consequences.

Architecturally this was wrong.

The project already had those proofs.

The correct question was not

``` text
How do we prove the whole old theory again from HilbertAxioms?
```

but

``` text
What is the smallest compatibility layer that lets the existing theory
remain the existing theory?
```

The bridge was therefore reduced to transport and realization code.

## 14. HilbertPlaneTheory remains the derived theory

After the cleanup, `HilbertPlaneTheory.lean` was changed at its dependency
boundary.

Its active import is now

``` text
import CGJteamLab.HilbertPlaneAPI
```

rather than a direct import of the frozen legacy axiom declarations.

The theorem bodies themselves were not ported theorem by theorem.

This preserves the division of responsibility:

``` text
HilbertAxioms
    source-faithful assumptions

HilbertPlaneAPI
    compatibility machinery

HilbertPlaneTheory
    derived plane mathematics
```

That separation is the principal result of the refactor.

## 15. What the successful build proves

After the import boundary was changed, `HilbertPlaneTheory.lean` compiled
without modification of its derived theorem corpus.

The complete project also passed

``` text
lake build
```

This establishes an important software-architectural fact:

> The compatibility boundary can be inserted without forcing a rewrite of
> the existing geometry library.

It does not by itself prove that every enriched legacy class has already been
reconstructed as a source-theorem package from Groups I-V.

That is a different mathematical question.

The current bridge already realizes the induced incidence and order layers and
provides the direct source-to-legacy transports needed for the next
compatibility stages. The frozen legacy declarations remain available through
`HilbertAxiomsWork.lean`.

This distinction is essential:

``` text
successful dependency migration
            !=
complete semantic reduction of every legacy interface field
```

The former has been achieved.

The latter should be addressed only where mathematically necessary, without
duplicating the existing plane theory.

## 16. Why the bridge should remain thin

The final shape of `HilbertPlaneAPI.lean` expresses a useful design principle.

A compatibility layer should contain:

``` text
representation maps
subtype constructions
transport lemmas
canonical realizations
local instances on induced objects
```

It should not contain:

``` text
a second order theory
a second Pasch theory
a second triangle-congruence theory
a second Euclidean plane theory
```

The distinction protects both source fidelity and maintainability.

If a theorem already belongs to `HilbertPlaneTheory`, moving a copy of its
proof into the compatibility layer would obscure rather than clarify the
dependency structure.

## 17. The architectural result

The project now has an explicit boundary between spatial Hilbert foundations
and planar working geometry:

``` text
Hilbert source geometry
(points, lines, planes)
          |
          | choose pi
          v
induced HilbertPlaneGeo pi
          |
          | compatibility transport
          v
legacy planar vocabulary
          |
          | existing proofs
          v
HilbertPlaneTheory
```

This is more precise than treating the old plane classes as though they were
literal transcriptions of Hilbert's axioms.

It also provides a reusable strategy for future work in higher dimensions:
planar theorems can be applied through an induced plane rather than promoted
incorrectly to ambient spatial axioms.

## 18. Current status

At the end of this stage:

- `HilbertAxioms.lean` remains the source-faithful Hilbert foundation;
- `HilbertAxiomsWork.lean` retains the frozen legacy plane declarations;
- `HilbertPlaneAPI.lean` is the compatibility and transport layer;
- a fixed Hilbert plane is represented by `HilbertPlaneGeo`;
- legacy incidence and order are realized on the induced plane;
- Group III segment data are transported directly where appropriate;
- same-side and ray representations are related explicitly;
- primitive source angle congruence maps forward to the legacy
  equivalence-closed relation;
- theorem-level plane geometry is not reimplemented in the adapter;
- `HilbertPlaneTheory.lean` imports the compatibility layer;
- the full Lean project builds successfully with this dependency boundary.

The next documentation task is to state the resulting foundational boundary
of the whole Hilbert route and to distinguish the new production architecture
from the historical architecture described in earlier research logs.

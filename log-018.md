# Log 018 - Refactoring the Hilbert and Suppes Architecture

## 1. Overview

The introduction of the Suppes route created an architectural problem that did not exist while the project followed only one axiomatic path.

The same high-level Finlay argument was now being approached through two different lower-level developments:

- the existing Hilbert-oriented route,
- the new Suppes-oriented route.

The immediate task was not yet to produce a final common architecture. It was to reorganize the files so that the two routes could be inspected and compared without destabilizing the reference Finlay proof.

This log records that intermediate architecture as it existed on 23 July.

---

## 2. The Hilbert-Oriented Route

One small but useful cleanup concerned imports.

`GeometryBase.lean` no longer needed to import `GeometryCore.lean` directly because the latter was already reached through `HilbertAxioms.lean`.

At this stage the dependency chain was:

```text
FinlayProof
    |
    v
MidsegmentParallel
    |
    v
GeometryBase
    |
    v
HilbertAxioms
    |
    v
GeometryCore
```

This diagram is historical. The file names and boundaries were still evolving and should not be read as the final architecture of the project.

The useful result was more modest: the dependency path from the high-level proof toward the Hilbert-oriented foundations became easier to inspect.

The modified chain was verified by recompiling `FinlayProof.lean`.

---

## 3. Consolidating the Suppes Files

The first Suppes development had been split across

```text
SuppesAxioms
    |
    v
SuppesCore
    |
    v
SuppesTheorems
```

At this early stage the distinction between `SuppesCore` and `SuppesTheorems` was not yet useful enough to justify the additional file boundary.

Their contents were therefore consolidated into

```lean
SuppesBase.lean
```

while `SuppesAxioms.lean` remained separate.

This was an implementation decision appropriate to the state of the project at that moment, not a claim about the final logical decomposition of the Suppes theory.

Later reverse engineering could split these responsibilities again if clearer boundaries emerged.

---

## 4. The Role of SuppesBase

At this stage `SuppesBase` combined two kinds of material:

1. Suppes-specific definitions and derived results,
2. compatibility machinery connecting them with the existing geometry vocabulary.

It contained, among other declarations:

```lean
SuppesParallel
suppes_parallel_of_parallelogram
SuppesMidsegmentBridge
```

This mixture is important historically.

`SuppesBase` was not yet a clean foundational layer. It was an experimental integration layer created so that the Suppes midsegment development could communicate with the existing Finlay environment.

In particular, importing `GeometryBase` into this layer meant that the experimental Suppes path was not yet logically isolated from the Hilbert-oriented development.

Therefore the architecture should not be interpreted as a reduction of Finlay to Suppes' axioms alone.

---

## 5. The Suppes Dependency Route

After the consolidation, `MidsegmentParallelSuppes.lean` could import

```lean
CGJteamLab.SuppesBase
```

and concentrate on the Suppes-based midsegment argument.

The resulting dependency graph was:

```text
FinlayProofSuppes
        |
        v
MidsegmentParallelSuppes
        |
        v
SuppesBase
   /           \
  v             v
GeometryBase   SuppesAxioms
     |              |
     v              |
HilbertAxioms       |
     |              |
     +------v-------+
            |
      GeometryCore
```

The important feature of this graph is precisely its imperfection.

The Suppes experimental branch still descended through `GeometryBase` and therefore through the Hilbert-oriented side of the library while also importing `SuppesAxioms`.

This made the next research question visible:

> Which parts of the Suppes path genuinely follow from Suppes, and which are being inherited through the shared interface?

The architecture itself exposed the problem.

---

## 6. Compilation and Dependency Hygiene

The refactoring also included smaller Lean-level cleanup.

For example, a theorem that did not require the section-level `HilbertIncidence` instance was explicitly marked with

```lean
omit [HilbertIncidence Geo] in
```

rather than silencing the linter globally.

This is a minor implementation detail, but it supports the larger objective of the reverse-engineering work: assumptions should remain visible and should not be carried through declarations unnecessarily.

After the refactoring, the relevant Hilbert-oriented and Suppes-oriented developments compiled.

Compilation established that the reorganization was technically consistent. It did not by itself establish logical independence of the two routes.

---

## 7. What This Refactoring Revealed

The original intention was to make the two midsegment implementations easier to exchange.

The resulting dependency graph showed that the deeper problem was not merely module substitution.

A common theorem name can hide substantially different foundational requirements.

Before the two routes can genuinely support the same high-level interface, the project must determine:

- which notions belong to the common synthetic language,
- which are specific to Hilbert,
- which are specific to Suppes,
- which bridge declarations are proved,
- which bridge declarations remain assumptions,
- whether the Suppes route can be detached from Hilbert-oriented dependencies.

This is a stronger and more precise problem than simply arranging imports.

---

## 8. Outlook

The immediate architectural goal remains to reduce the difference between the two midsegment interfaces.

But the experiment has shown that import-level compatibility is not sufficient.

The next stage must trace the Suppes branch downward and determine the exact logical status of every dependency crossing from `SuppesBase` into the existing geometry interface.

Only after that analysis will it be meaningful to ask whether the two midsegment realizations can be selected by changing an import while leaving the high-level Finlay proof unchanged.

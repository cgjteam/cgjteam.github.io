# Log 052 --- The Foundational Boundary after the Hilbert Refactor

## From one mixed Hilbert layer to a stratified production architecture

The Hilbert refactor documented in Logs 050 and 051 changes the meaning of
the foundational boundary of the project.

Earlier project documentation described a simpler route:

``` text
HilbertCore
    |
    v
HilbertAxioms
    |
    v
HilbertInterface
```

That description was useful for the older implementation, but it no longer
captures the production dependency structure.

The active route is now better represented as

``` text
HilbertCore
    |
    v
HilbertAxioms
    |
    v
HilbertPlaneAPI
    |
    v
HilbertPlaneTheory
    |
    v
HilbertGrundlagen
    |
    v
HilbertInterface
    |
    v
HilbertBookZero
    |
    v
Euclid and other applications
```

There is also one compatibility side dependency:

``` text
HilbertAxiomsWork
       |
       v
HilbertPlaneAPI
```

`HilbertAxiomsWork` is not the new foundation. It preserves the legacy plane
declarations required by the existing theorem corpus.

The purpose of this log is to state the new boundary clearly before the
project returns to applications in Euclid, Wyler, Coxeter, and related
developments.

## 1. The refactor separates five different mathematical roles

The active Hilbert route now distinguishes at least five layers that should
not be conflated:

``` text
1. primitive geometric language
2. source-faithful Hilbert axioms
3. compatibility with the legacy plane API
4. derived plane theory
5. working synthetic language
```

In file form:

``` text
HilbertCore.lean
HilbertAxioms.lean
HilbertPlaneAPI.lean
HilbertPlaneTheory.lean
HilbertGrundlagen.lean / HilbertInterface.lean / HilbertBookZero.lean
```

This is not merely a reorganization of filenames.

Each layer answers a different mathematical question.

## 2. HilbertCore is the representation boundary

`HilbertCore.lean` defines the common geometric carrier

``` text
Geo
```

with primitive types

``` text
Point
Line
```

and primitive relations

``` text
OnLine
Between
SegmentCongruent
UnorientedAngleCongruent
```

It also defines representation-level constructions such as rays, segments,
angles, and the derived four-point segment-congruence interface.

The crucial distinction is:

> HilbertCore gives the language in which geometry is expressed, but it does
> not yet impose Hilbert's geometric axioms on that language.

This remains the first foundational boundary.

Representation choices made here can have logical consequences.

For example, an unoriented segment is represented by an unordered pair of
endpoints. Likewise, the public angle representation uses unordered boundary
rays.

Such consequences are representation laws, not Hilbert axioms.

The refactor does not change this role.

## 3. HilbertAxioms is now a source layer in the strict sense

The new `HilbertAxioms.lean` has a much narrower and clearer responsibility
than the file bearing that name in the older architecture.

It records Hilbert's five axiom groups in source-oriented form:

``` text
Group I     incidence
Group II    order
Group III   congruence
Group IV    parallel uniqueness
Group V     continuity
```

The file includes the spatial incidence language required by I.1-I.8,
including explicit planes and point-plane incidence.

It also preserves the source-sensitive distinctions established in Log 050:

``` text
Pasch is planar.
Primitive angle congruence remains primitive.
Group IV states uniqueness, not existence.
V.2 is represented as a maximality principle.
```

The role of this layer is therefore:

``` text
HilbertCore
    |
    | vocabulary
    v
HilbertAxioms
    |
    | genuine source-faithful assumptions
    v
Hilbert geometry
```

No working-plane convenience should be inserted here merely because a
downstream theorem would become easier to state.

## 4. The source layer is not the legacy plane interface

This is the main conceptual correction.

The old project API contains classes such as

``` text
HilbertIncidence
HilbertPlaneIncidence
HilbertOrder
HilbertCongruence
HilbertEuclideanPlane
HilbertArchimedeanPlane
```

These are valuable working interfaces, but they are not literal copies of the
new source layer.

Several differences are structural.

The legacy API is planar.

The new source system contains explicit spatial incidence.

The legacy order interface suppresses the plane parameter in Pasch.

The source system keeps it explicit.

The legacy angle language uses

``` text
Geo.AngleCongruent
```

built from an equivalence closure.

The source system uses the primitive relation

``` text
Geo.UnorientedAngleCongruent
```

through `HilbertGrundlagenAngleCongruent`.

Therefore the architecture must not be simplified to

``` text
new axioms = old classes with new names
```

They are different interfaces with different purposes.

## 5. HilbertAxiomsWork is a migration artifact with a precise role

`HilbertAxiomsWork.lean` retains the frozen legacy declarations needed to
compile the existing plane theory.

Its presence can easily be misunderstood.

It is not a competing foundation.

It is not the file against which future source-fidelity questions should be
judged.

It is not the place to add new mathematical results.

Its role is:

``` text
preserve legacy signatures
        |
        v
allow compatibility transport
        |
        v
avoid rewriting the established theorem corpus
```

This makes it a controlled migration artifact.

The long-term mathematical authority lies below it, in
`HilbertAxioms.lean`, and above it, in the already proved theorem corpus.

## 6. HilbertPlaneAPI is the interpretation boundary

`HilbertPlaneAPI.lean` is the new structural boundary between source geometry
and the older planar language.

Its task is not to prove ordinary Euclidean geometry.

Its task is to interpret the source-faithful structure in a form that can be
consumed by the legacy plane theory.

The central construction is the induced geometry

``` text
HilbertPlaneGeo Geo pi
```

for a fixed source-faithful Hilbert plane `pi`.

This produces:

``` text
ambient Hilbert space
       |
       | choose pi
       v
points and lines lying in pi
       |
       v
induced planar geometry
       |
       v
legacy plane API
```

The important point is that the planar restriction is mathematical, not
cosmetic.

It is what makes source II.4 compatible with the old planar Pasch interface
without falsely promoting a plane axiom to ambient three-dimensional
geometry.

## 7. Local induced instances replace unsafe ambient instances

The refactor establishes a useful typeclass rule.

Where a theorem is genuinely planar, the preferred object is not a global
ambient instance such as

``` text
HilbertOrder Geo
```

constructed by forgetting the spatial setting.

Instead, the correct target is an instance on

``` text
HilbertPlaneGeo Geo pi
```

for a fixed plane.

This avoids a recurrent formalization error:

``` text
theorem true in every plane
        |
        X
        v
theorem postulated globally in space
```

The induced-plane construction preserves the missing geometric parameter in
the type itself.

This principle will be relevant again in the three-dimensional and
dimension-free parts of the project.

## 8. HilbertPlaneTheory remains the theorem layer

`HilbertPlaneTheory.lean` contains the established body of derived plane
geometry.

Its current import begins with

``` text
import CGJteamLab.HilbertPlaneAPI
```

The theorem corpus was not rewritten during the foundational refactor.

This determines the correct division:

``` text
HilbertAxioms
    assumptions

HilbertPlaneAPI
    interpretation and compatibility

HilbertPlaneTheory
    proofs
```

This distinction is one of the most important results of the migration.

A compatibility problem should first be treated as a representation or
dependency-boundary problem.

It should not automatically trigger a new proof of a theorem that already
exists in `HilbertPlaneTheory`.

## 9. A successful build has a precise meaning

After redirecting `HilbertPlaneTheory.lean` through the compatibility layer,
the file compiled successfully.

The complete project also passed

``` text
lake build
```

This verifies the production dependency migration.

It shows that the existing downstream theorem corpus can coexist with the new
source layer.

However, the build should not be interpreted as a stronger mathematical
claim than it establishes.

In particular:

``` text
dependency compatibility
        !=
complete proof that every enriched legacy interface field
is already reduced semantically to the new source axioms
```

The bridge contains genuine source-to-legacy realizations and transport
results, but the frozen legacy declarations still participate in the current
migration architecture.

This remaining distinction should stay visible in future audits.

## 10. HilbertGrundlagen is now above the plane theory

The current production file

``` text
HilbertGrundlagen.lean
```

imports

``` text
HilbertPlaneTheory
```

It then exposes Hilbert-related theorem packages and local prerequisites used
by the higher synthetic interface.

This means that, in the active import graph, `HilbertGrundlagen` is no longer
the foundational axiom file despite its name.

It belongs above the derived plane theory.

This is an example of why architectural status must be determined from the
current dependency graph and declaration content, not from filenames alone.

There is also a stale introductory comment in the file stating that it
imports only `HilbertAxioms`. The actual import is `HilbertPlaneTheory`.
That comment should be corrected as part of the documentation cleanup.

## 11. HilbertInterface is the working-language boundary

`HilbertInterface.lean` currently imports

``` text
HilbertGrundlagen
```

and provides the higher-level language used by synthetic proofs.

Examples include notions such as

``` text
IsMidpoint
HilbertIsMidpoint
IsIntersection
IsMedian
OppositeSidesParallel
OppositeSidesCongruent
```

and a larger body of theorem-level operations.

Its role remains close to that described in the older Log 023:

``` text
foundational / derived Hilbert geometry
              |
              v
        HilbertInterface
              |
              v
recognizable synthetic operations
```

What has changed is the structure below it.

The interface is no longer immediately above a monolithic
`HilbertAxioms.lean`.

It now sits above an explicit source layer, compatibility layer, and derived
plane-theory layer.

## 12. Book Zero remains above the interface

`HilbertBookZero.lean` imports

``` text
HilbertInterface
```

and continues to serve as the working elementary synthetic corpus used by
later Euclidean reconstructions.

This gives the present lower-to-upper hierarchy:

``` text
primitive representation
        |
        v
source axioms
        |
        v
plane interpretation
        |
        v
derived plane theory
        |
        v
synthetic interface
        |
        v
Book Zero
        |
        v
Euclid
```

This hierarchy clarifies why Book Zero should not normally need to know
whether a low-level theorem originated directly in a source axiom, an induced
plane transport, or a longer Hilbert plane derivation.

Those questions remain traceable below the working-language boundary.

## 13. The old Logs 021-023 are now historical documents

Logs 021, 022, and 023 were accurate reconstructions of the architecture at
the time they were written.

They should not simply be deleted.

They document the evolution of the project and explain how the former design
was understood.

But several statements in them are no longer current production
descriptions.

In particular, the older documentation presents

``` text
HilbertCore
    |
    v
HilbertAxioms
    |
    v
HilbertInterface
```

and describes `HilbertAxioms.lean` as containing both the old axiom classes
and a large derived plane theory.

After the refactor, that material is distributed across:

``` text
HilbertAxioms
HilbertAxiomsWork
HilbertPlaneAPI
HilbertPlaneTheory
```

Logs 050-052 therefore form the new documentation checkpoint.

The older logs remain valuable as development history.

## 14. Geometry.md is also now historically stale in its Hilbert section

The current `Geometry.md` still describes the earlier Hilbert architecture.

It presents

``` text
HilbertCore
    |
    v
HilbertAxioms
    |
    v
HilbertInterface
```

and lists the legacy class hierarchy directly under `HilbertAxioms.lean`.

That is no longer an accurate description of the production file structure.

The next documentation refactor should update `Geometry.md` so that the
Hilbert section distinguishes:

``` text
HilbertCore
HilbertAxioms
HilbertPlaneAPI
HilbertPlaneTheory
HilbertGrundlagen
HilbertInterface
HilbertBookZero
```

and gives `HilbertAxiomsWork` an explicitly transitional compatibility role.

This is not merely cosmetic.

`Geometry.md` is supposed to answer the architectural question "What exists
and how is it related?" If it presents the old dependency chain, future
audits will start from the wrong boundary.

## 15. Source fidelity and proof usability now occupy different axes

The new architecture reveals two independent design questions.

The first is foundational:

``` text
How faithfully does the bottom layer represent Hilbert's source system?
```

The second is operational:

``` text
How convenient is the upper layer for proving synthetic geometry?
```

These questions need not have the same answer at the same layer.

A source-faithful axiom system may be awkward for everyday proofs.

A useful working interface may package many derived facts.

That is not a defect if the dependency between them is explicit.

The present architecture therefore separates:

``` text
historical fidelity
        |
        v
HilbertAxioms

proof engineering
        |
        v
HilbertPlaneTheory
HilbertInterface
HilbertBookZero
```

with `HilbertPlaneAPI` providing the interpretation boundary between them.

## 16. The new boundary also clarifies dimensional reasoning

The older plane API made it easy to think of Hilbert geometry as essentially
planar.

The new source layer restores I.4-I.8 and therefore makes spatial incidence
visible.

This changes how later three-dimensional work should be audited.

A theorem using only a fixed plane may still use the established plane theory
through `HilbertPlaneGeo`.

A theorem genuinely involving several planes must remain in the spatial
language.

Thus there are now two different movements available:

``` text
spatial Hilbert geometry
        |
        +--> restrict to pi --> use plane theory
        |
        `--> remain spatial --> prove a genuine 3D theorem
```

This is especially relevant for Book XI, Wyler, Smith, and Coxeter-related
developments.

The refactor therefore does more than clean up Book I foundations. It gives
the project a more disciplined way to distinguish planar and spatial
arguments.

## 17. The new foundational checkpoint

Before proceeding to applications, the Hilbert route can now be summarized
by the following checkpoint.

``` text
HilbertCore

        |
        v

HilbertAxioms
    source-faithful Groups I-V

        |
        v

HilbertPlaneAPI
    induced-plane interpretation and compatibility transport
    + frozen legacy declarations from HilbertAxiomsWork

        |
        v

HilbertPlaneTheory
    existing derived plane geometry

        |
        v

HilbertGrundlagen
    theorem packages tied to the Hilbert development

        |
        v

HilbertInterface
    reusable synthetic API

        |
        v

HilbertBookZero
    elementary working language

        |
        v

Euclid / Finlay / later applications
```

This should be the reference architecture for the next stage.

## 18. What is stable and what is still transitional

The current checkpoint contains both stable mathematical layers and one
explicitly transitional mechanism.

Stable in role:

``` text
HilbertCore
HilbertAxioms
HilbertPlaneTheory
HilbertInterface
HilbertBookZero
```

New stable boundary:

``` text
HilbertPlaneAPI
```

Transitional compatibility support:

``` text
HilbertAxiomsWork
```

The word "transitional" should not be interpreted as "delete immediately."

Removing it safely would require a separate semantic audit of every legacy
class field and every downstream consumer.

The current achievement is more modest and more useful:

> The source-faithful foundation is now present in production without
> destabilizing the existing proof corpus.

That is enough to continue mathematical work while preserving a clear record
of the remaining compatibility debt.

## 19. Documentation consequences

The documentation should now follow the same separation as the code.

Research Logs should explain:

``` text
why the separation was introduced
what logical distinctions it preserves
what migration choices were made
```

`Geometry.md` should record:

``` text
the current files
the current dependency graph
the status of legacy compatibility declarations
```

The Lean source should remain responsible for:

``` text
the executable definitions
the transport constructions
the proofs
```

This restores the project methodology stated in `ARCHITECTURE.md`:

``` text
Research Logs  -> why
Geometry.md    -> what
Lean source    -> how
```

The foundational refactor is therefore incomplete as documentation until
`Geometry.md` is synchronized with the new production graph.

## 20. Current status

At the end of Logs 050-052:

- `HilbertCore.lean` remains the primitive and representation layer;
- `HilbertAxioms.lean` is the source-faithful Hilbert axiom layer;
- Groups I-V are separated from the old working plane hierarchy;
- `HilbertAxiomsWork.lean` preserves frozen legacy declarations for
  compatibility;
- `HilbertPlaneAPI.lean` interprets the source system on an induced plane and
  bridges to the legacy plane vocabulary;
- `HilbertPlaneTheory.lean` remains the existing derived theorem corpus;
- `HilbertGrundlagen.lean` sits above the plane theory in the active import
  graph;
- `HilbertInterface.lean` remains the reusable synthetic-language boundary;
- `HilbertBookZero.lean` remains the elementary working layer above that
  interface;
- the full project builds successfully with the new dependency chain;
- older Logs 021-023 are now historical descriptions of the pre-refactor
  architecture;
- the Hilbert section of `Geometry.md` still needs synchronization with the
  new production structure.

The foundational phase is therefore sufficiently explicit to proceed to
applications.

Before doing so, the remaining documentation task is to update
`Geometry.md` so that future work begins from the same architecture that the
Lean project now uses.
